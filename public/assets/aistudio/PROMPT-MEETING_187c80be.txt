2. Product Vision

Build an Android meeting recorder and transcription workspace that captures spoken conversations, converts them into timestamped text, and uses AI to organize the complete transcript into a readable, professionally structured document.

The defining requirement: this application must NOT reduce a meeting to a summary.

It must preserve the conversation's substantive content, including:

- Introductions and small talk.
- Questions and answers.
- Repetitions and informal language.
- Clarifications, interruptions, and changes of topic.
- Disagreements, explanations, and incomplete thoughts.
- Relevant conversational context, even when it is not directly related to the meeting agenda.

The AI may improve punctuation, paragraph structure, readability, and document organization. It must not silently remove substantive information, invent statements, or turn uncertain speech into fabricated facts.

The original transcript must remain recoverable even when AI processing fails or produces an unsatisfactory result.

4. Platform and Architecture

Build a native Android application using the supported Google AI Studio Android environment.

Preferred technologies:

- Kotlin.
- Jetpack Compose and Material 3.
- A single Activity and a single supported Android module.
- ViewModel and lifecycle-aware state management.
- Kotlin coroutines and Flow where appropriate.
- Room for structured local data.
- Android-supported file storage and document export.
- Foreground Service for active microphone recording.
- WorkManager for appropriate deferrable background tasks, such as retrying eligible processing jobs.

Use compatible, maintained dependencies and verify versions against the environment before adding them.

Keep responsibilities separated even if the platform requires a single module. Organize code into appropriate packages for presentation, domain logic, data access, recording, transcription, AI processing, and export.

Avoid unnecessary abstraction, excessive dependencies, and premature enterprise architecture. However, do not put recording logic, database operations, networking, and document processing directly into composable UI functions.

The UI must remain responsive while recording, saving, or processing transcripts.

5. Core Architectural Principle: Local-First and Failure-Resilient

The recording pipeline must not depend on the AI pipeline succeeding.

Use this conceptual architecture:

Audio Capture → Local Audio Persistence → Transcription Jobs → Raw Transcript → AI Document Processing → Exportable Document.

Implement the details according to platform constraints.

Audio persistence

- Write recorded audio incrementally to local files.
- Never accumulate an entire long recording in RAM.
- Persist recording metadata and processing state.
- Use stable recording and segment identifiers.
- Maintain start and end timestamps where available.
- Track processing status and failures.
- Recover unfinished work after process termination or application restart where feasible.
- Avoid corrupting or overwriting existing audio when pausing, resuming, or recovering.
- Check available storage and report insufficient space clearly.
- Allow users to delete audio and documents independently, with explicit confirmation where appropriate.

Do not delete original audio automatically after transcription. The default is to retain it until the user explicitly deletes it.

Do not promise perfect recovery from every possible device failure. Design for recoverability and document the remaining limitations.

Background recording

Implement the appropriate Android microphone foreground service and notification behavior.

Handle permissions, lifecycle transitions, service startup restrictions, and Android-version differences correctly.

The intended user flow is:

1. User opens the application.
2. User grants the necessary microphone permission.
3. User explicitly starts recording.
4. Recording continues while the screen is off or another application is in the foreground, subject to Android restrictions.
5. The user can pause, resume, or stop through the application.
6. Provide appropriate notification controls if supported and reliable.
7. Persist recording state and recover gracefully after interruptions.

Never bypass Android privacy controls or attempt hidden recording.

Do not confuse persistent background recording with WorkManager jobs. Choose the correct mechanism for each responsibility.

6. Speech-to-Text Strategy

Use a hybrid, local-first architecture.

The default objective is high-quality cloud transcription with local audio persistence and a recoverable processing queue.

First, evaluate available options:

- Gemini transcription capabilities supported by the current environment.
- Android SpeechRecognizer as a potential alternative or fallback.
- Local transcription engines only if their integration, resource requirements, and performance are realistic.

Prefer a verified transcription capability that supports verbatim output, timestamps, and speaker information when available.

Do not assume that every model supports word-level timestamps, speaker diarization, incremental streaming, or long recordings. Verify each capability independently.

Incremental transcription

Design the system to process audio in manageable segments when supported.

Each segment should have:

- A stable identifier.
- Its recording identifier.
- Start and end time.
- Processing status.
- Transcript content when available.
- Error information when processing fails.

Prevent duplicate segments, overlapping timestamps, and accidental loss during retries.

If the chosen provider cannot perform genuine live streaming, implement a truthful alternative such as periodic chunk processing or post-recording transcription.

Do not simulate real-time transcription by displaying fabricated or prerecorded text.

Indonesian-language quality

Use Bahasa Indonesia as the primary language and mixed Indonesian-English conversation as a major test case.

Support language selection or automatic detection only where the chosen engine actually supports it.

Preserve technical terminology, names, abbreviations, and English phrases as accurately as possible. Provide a way to correct transcription mistakes.

When speech is unintelligible, mark it appropriately rather than inventing a sentence.

Authentication and privacy

Google AI Studio Android projects are client-side applications. Inspect the supported Firebase AI Logic and App Check integration paths where appropriate.

Never hardcode a private server API key, secret credential, or unrestricted privileged token into the APK.

Use an officially supported secure client integration where available. If a feature requires a backend that the environment cannot provide, document the constraint and implement the best secure, supported alternative.

Do not transmit audio to a cloud service without clearly explaining that behavior to the user.

7. Transcript and Document Data Model

Treat the raw transcript, readable transcript, and AI-organized document as separate representations.

A. Raw transcript

Preserve the closest available output from the speech recognition engine, together with source segment references, timestamps, speaker labels, and confidence metadata when provided.

Never pretend that raw speech-recognition output is a perfect verbatim record. Recognition engines can omit or misrecognize words.

Do not overwrite the raw transcript when correcting or formatting the text.

B. Readable transcript

Allow punctuation correction, paragraph restructuring, and limited readability improvements while preserving substantive information.

The user should be able to choose between:

- Verbatim: preserve filler words, repetitions, informal expressions, and incomplete speech as accurately as possible.
- Readable: improve readability without removing substantive statements or changing meaning.

Retain references to original segments and timestamps wherever possible.

C. AI-organized meeting document

Allow the AI to organize the complete transcript into a professional document using headings, paragraphs, topic sections, and speaker labels.

Potential sections include:

- Meeting information.
- Opening and introductions.
- Discussion sections.
- Questions and responses.
- Clarifications and disagreements.
- Closing conversation.

Use sections only when appropriate. Do not force every conversation into a rigid template.

Preserve small talk and other conversational content. Do not silently discard it because it appears unimportant.

The document must remain complete, not merely a list of key takeaways.

AI integrity requirements

- Never fabricate facts, quotes, decisions, attendees, or timestamps.
- Never claim a decision was agreed upon when participants only discussed it.
- Do not create action items unless they are supported by the transcript.
- Preserve uncertainty and ambiguity.
- Avoid unnecessary paraphrasing.
- Maintain traceability between organized paragraphs and their source transcript segments.
- Validate AI output before saving it.
- Keep the original transcript recoverable after every AI operation.

Use structured model output where supported, with explicit source references and validation. If a generated document cannot be validated, retain the original and report the problem rather than silently replacing it.

8. AI Document Editing

Provide a document editor where users can:

- Review the full organized transcript.
- Edit text manually.
- Rename speakers.
- Correct transcription errors.
- Reprocess selected content.
- Change document organization or writing style using custom instructions.
- Restore the previous version when feasible.
- Compare generated content with its source transcript.

Custom instructions must not override the core data-integrity rules.

Avoid unnecessary model calls. Do not send the entire recording or transcript repeatedly when only a small section needs correction, unless required by the chosen model.

Keep generated content distinguishable from original speech data.

11. Export and Storage Reliability

Use a clear persistence strategy.

Room should store structured metadata and transcript records. Audio should use suitable local file storage. Do not store large audio blobs in ordinary UI state or repeatedly load entire recordings into memory.

Use appropriate Android file access and document-sharing mechanisms.

The application must preserve data across ordinary navigation and process restarts.

Implement reasonable transactional boundaries and recovery logic so that a failed export or AI operation does not corrupt the source document.

Where necessary, use temporary files and atomic replacement to avoid leaving partially written final exports.
